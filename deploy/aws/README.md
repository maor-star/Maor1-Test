# פריסה ל-AWS (EC2)

פריסת אפליקציית ניהול המשרד על מכונת EC2, מאחורי Caddy עם סיסמה ו-HTTPS.

> **לא נבדק.** הסקריפטים נכתבו בלי גישה ל-AWS, כך שלא הרצתי אותם אפילו פעם אחת.
> ההיגיון נכון והפקודות סטנדרטיות, אבל צפה לאפשרות שמשהו ייפול בפעם הראשונה.
> כל שלב מדפיס מה הוא עושה — אם משהו נשבר, שלח לי את הפלט ואתקן.

## למה EC2 ולא S3 + CloudFront

אפליקציית ניהול הבית נפרסה על S3 + CloudFront כי היא קובץ HTML אחד שרץ בדפדפן,
עם הנתונים ב-`localStorage`. אין שם שרת.

האפליקציה הזאת היא שרת Express עם בסיס נתונים SQLite על הדיסק ו-15 נתיבי API.
S3 ו-CloudFront לא מריצים קוד שרת, ולכן צריך מכונה.

## מה נוצר

| משאב | תפקיד | עלות משוערת |
|---|---|---|
| EC2 `t3.micro` | מריץ את האפליקציה | ~$8/חודש |
| דיסק EBS 20GB gp3 | מערכת + בסיס נתונים | ~$1.6/חודש |
| Elastic IP | כתובת שלא משתנה | חינם כל עוד מחוברת למכונה |
| Security Group | 80/443 לכולם, 22 רק מה-IP שלך | חינם |

בערך **$10 לחודש**. בחשבון חדש חלק מזה עשוי להיכנס ל-Free Tier.

## דרישות מקדימות

```bash
brew install awscli
aws configure          # Access Key, Secret, אזור
aws sts get-caller-identity   # בדיקה שזה עובד
```

## פריסה

מתוך תיקיית הריפו:

```bash
DOMAIN=maor-office.duckdns.org bash deploy/aws/deploy.sh
```

אפשר גם בלי דומיין — אז הגישה תהיה ב-HTTP לפי IP, **בלי הצפנה**:

```bash
bash deploy/aws/deploy.sh
```

הסקריפט מבצע: בדיקות מקדימות ← מפתח SSH ← Security Group ← מכונה ← Elastic IP ←
העלאת האפליקציה ← התקנה ← הדפסת הכתובת והסיסמה.

**הסיסמה מודפסת רק פעם אחת בסוף. שמור אותה.** להגדרת סיסמה משלך:

```bash
APP_PASSWORD='my-password' DOMAIN=maor-office.duckdns.org bash deploy/aws/deploy.sh
```

## סדר הפעולות עם דומיין

1. היכנס ל-[duckdns.org](https://www.duckdns.org), התחבר, וצור שם — למשל `maor-office`.
   בשלב הזה אפשר להזין כל IP.
2. הרץ את `deploy.sh` עם `DOMAIN=maor-office.duckdns.org`.
3. בסוף הוא ידפיס את הכתובת האמיתית. חזור ל-DuckDNS ועדכן אותה.
4. תוך כמה דקות Caddy ינפיק תעודת SSL לבד. אין מה לעשות — הוא מנסה שוב מעצמו.

## עדכון האפליקציה

אותה פקודה בדיוק. הסקריפט מזהה שהמכונה קיימת, מעלה את הקוד החדש ומפעיל מחדש.
**תיקיית `data/` לא נדרסת** — בסיס הנתונים נשאר.

## גיבוי

הנתונים כולם בקובץ אחד. אין גיבוי אוטומטי:

```bash
ssh -i ~/.ssh/office-app-key.pem admin@<IP> \
  'sudo cat /opt/office-app/data/office.db' > office-backup-$(date +%F).db
```

שווה לתזמן את זה ב-`cron` על המק, או להעלות ל-S3 מהשרת.

## תחזוקה

```bash
ssh -i ~/.ssh/office-app-key.pem admin@<IP>          # התחברות
sudo systemctl status office-app                      # סטטוס
sudo journalctl -u office-app -f                      # לוגים חיים
sudo systemctl restart office-app                     # הפעלה מחדש
sudo journalctl -u caddy -n 50                        # לוגים של הפרוקסי (תעודות SSL)
```

## מחיקה

```bash
bash deploy/aws/teardown.sh
```

מוחק מכונה, Elastic IP, Security Group ומפתח. **מוחק גם את בסיס הנתונים** — גבה קודם.

## על האבטחה

לאפליקציה עצמה אין שום מנגנון אימות. כל 15 נתיבי ה-API ב-`server.js` פתוחים לחלוטין:
עובדים, שעות, הוצאות והכנסות — קריאה וכתיבה, בלי סיסמה.

הפריסה הזאת מכסה את זה בשכבה חיצונית: Caddy דורש שם משתמש וסיסמה לפני שבקשה
מגיעה לאפליקציה בכלל. זה פתרון אמיתי לחשיפה לאינטרנט, והוא לא דורש שינוי קוד.

מה שהוא **לא** נותן:

- אין משתמשים נפרדים. סיסמה אחת משותפת לכולם, ואין לדעת מי עשה מה.
- אין הרשאות. כל מי שנכנס רואה ועורך הכול.
- הסיסמה מגינה על הגישה, לא על הנתונים עצמם — קובץ ה-SQLite על הדיסק אינו מוצפן.
- מי שמתחבר ל-SSH עוקף את הכול. לכן פורט 22 מוגבל ל-IP שלך בלבד.

אם המערכת תשמש כמה עובדים לאורך זמן, מסך התחברות אמיתי עם משתמשים נפרדים הוא
השלב הבא הנכון. הסיסמה הזאת היא פתרון סביר להיום, לא ארכיטקטורה סופית.

**שים לב:** פורט 22 פתוח רק ל-IP שממנו הרצת את הסקריפט. אם ה-IP שלך משתנה
(בית, נייד, רשת אחרת) — SSH יפסיק לעבוד. הרצה חוזרת של `deploy.sh` מוסיפה
את הכתובת החדשה אוטומטית.
